# 公开任务失败分析：先纠正产品假设

日期：2026-10-11。依据固定实现 `9659fb2` 的
[20 项原始结果](../evals/public_swe/results/2026-10-11-development-remaining20/README.md)、
实际发送 context、原始 API 记录和候选源码。
[输入审计数据](../evals/public_swe/results/2026-10-11-development-remaining20/context-audit.json)
另列测量口径和任务 ID。本文没有新增模型调用，也没有使用正式 200 项。

当前没有证据证明 HandoffSieve 优于强摘要。原文引用正确、packet 格式有效和符合预算，
只能证明这些局部性质，不能证明接管内容足够，也不能替代任务成功。

## 1. 先拆清楚 5/20 与 8/20 的差额

| 强摘要成功、HandoffSieve 未成功的任务 | HandoffSieve 实际停止原因 |
|---|---|
| `pydata__xarray-6721` | 必要 packet 估计 4,266 tokens，超过 4,000，未启动 coder |
| `scikit-learn__scikit-learn-13496` | 接收过程 provider 503 |
| `sphinx-doc__sphinx-8595` | 接收过程 provider 503 |

这是两项服务故障和一项产品预算拒绝，三项均没有可验收的 HandoffSieve 修复候选。
其余任务的二值验收结果两组一致。不能把差额直接解释成三个更差的代码修复；也不能
删掉故障和预算失败，把工程可用性问题隐藏掉。排除任一条件有服务错误的同题 10 项
事后诊断仍为完整历史 5/10、强摘要 6/10、HandoffSieve 5/10，不替代原始分母。

xarray 的[单独纠正接管](../evals/public_swe/results/2026-10-11-budget-takeover-v2/README.md)
已经以 3,830-token 包通过官方验收，但仅一次新接收试验、基线复用，不覆盖原始失败。
正式测试也不能用有利复测替代第一次记录。

## 2. 真正可量化的核心劣势：比强摘要更大，准备更贵

同一 11 项均有实际接收 context 的子集（含后来服务失败的接收请求，不是 11 项成功任务）：

| 指标 | 强接收需求摘要 | HandoffSieve 原文选择 |
|---|---:|---:|
| 平均 handoff 估计 tokens，包含目标与 JSON | 1,226.09 | 2,563.91 |
| 一次准备调用的合计 provider input tokens | 74,185 | 118,440 |
| 一次准备调用的合计 provider output tokens | 9,334 | 5,605 |
| 准备合计 provider tokens | 83,519 | 124,045 |

HandoffSieve 在这个匹配子集里 context 约为强摘要的 **2.09 倍**，准备合计已报告 tokens
高约 **48.52%**。这批数据不支持“原文提取天然更便宜”。它减少了完整历史，却没有达到
一个好的接管摘要的密度。接收阶段费用不能直接用不等量服务失败后的全组总量比较；
usage 也不是账单。任务 ID 在 20 项 summary 的 `complete_three_condition_context_subset_task_ids` 中。

### 直接观察到的浪费

`django__django-13212`：强摘要为 1,147 tokens，packet 为 3,754。packet 保留了
`validators.py` 的第 1–241 行，包含导入、初始化、属性及已调查的 validator 实现；
又保留完整研究 finish note。源码 content 本身估计 2,552 tokens。部分信息有用，但
“已读到且有关联”不能自动等同于“接管必须重新携带”。接收方仍可读取同一源码仓库。

该匹配子集的 11/11 packet 都保留了至少一个原始 action JSON 字符串，里面包着研究
`note`、`operation` 和空操作字段。这种传输格式进入任务视图，降低可读性并增加开销；
它不是 context 大两倍的唯一原因。主问题仍是大量源码和已有研究说明的重复。

## 3. 当前抽象的取舍有问题

**已证实的实现限制：**

- 模型只选原文，不能把散落观察整理成新的简短接管说明。
- 两条统一的宽泛 `needs` 覆盖“源码位置/行为”及“发现/待办”，没有逐任务的可检验接管需求。
- 任一 `need_indices` 引用会把对应条目固定为必要内容。模型把很多相关段落都用于覆盖时，
  本地只能保护或拒绝，不能知道哪些真能帮助接管。
- 连续源码窗口改善片段完整性，也增大选择颗粒；更多保留不等于更多任务价值。
- 原文准确复制并不保证原文里的研究结论正确；发送方本身也可能猜错。

**需要实验验证的解释：** 强摘要的优势可能来自把观察组织成下一步行动、明确未确认事项，
而原文集合要求接收方自己重新综合。这与当前数据一致，但没有被消融实验单独证实。
不能据此宣称已经发现唯一因果机制，也不能把所有共同失败归因于压缩。

因此不应继续把“禁止一切改写”当普遍最优原则。准确 API、约束、关键代码与失败输出应
保留原文；其他材料可以有简短语义说明，并引用其来源。引用有效不代表自动证明语义，
未知内容仍需显式标记。默认是否采用混合路径，应由强摘要对照的实际质量和总成本决定。

## 4. 自建执行器正在妨碍判断接管质量

当前 coder 只会列文件、搜文本、读源码和精确替换，不能运行复现脚本或测试；编辑成功
仅意味着字符串替换发生。`django__django-13212` 的强摘要候选存在可直接解析发现的
`IndentationError`，接收方提交前没有得到这个反馈。三组共同失败的四项 Django 任务
不能直接作为信息被选择器删错的证据。

16 项研究采集成功的任务均主动 finish，实际使用 4–7 次源码操作，**0/16 用完 8 次额度**。
未充分调查不能一概归因于额度过小。要检查它是否覆盖调用方、初始化关系和原项目测试，
以及 coder 后来是否反复补做发送方应完成的调查。

现有项目值得直接参考的能力：

- [mini-swe-agent 默认执行流程](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/config/default.yaml)
  要求找源码、复现问题、修改、重新验证和检查边界；
  [执行循环](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py)
  把实际环境输出送回下一轮。应优先复用成熟的执行环境进行评测，而不是继续为受限
  自建 runner 拼一个完整编码 Agent。评测接入不增加产品框架 adapter。
- [LLMLingua 的公开接口](https://github.com/microsoft/LLMLingua)已有目标感知排序、预算分配和
  区分可压缩/不可压缩内容的设计。我们应学习任务相关的分层处理，而不是将它的公开
  RAG/压缩成绩当成本项目代码接管的直接比较结果。

目前的表格只比较本项目同模型的三条输入路径；尚未与上述项目做同条件直接评测。

## 5. 调整推进顺序

1. **先修产品路线。** 在现有 `ReceiverContract` / `HandoffPacket` 内试验简短行动说明 +
   必要原文证据。清楚表达已确认发现、未确认事项、相关文件和接下来要做什么；整文件内容
   不因相关就自动必带。用已有开发状态对比强摘要，保留原文路径作消融，不新增平台。
2. **同时复用成熟接收执行环境。** 三组有相同工具、源码起点和预算，能得到各自的真实
   可见复现/测试反馈。原项目旧测试未必覆盖新需求，测试反馈不等于隐藏最终验收；不能
   盲目把意图改变的旧断言当成要求撤销修复。最终仍独立使用官方验收。
3. **检查调查质量，不盲目加额度。** 核对提前 finish 与 coder 补查轨迹，识别遗漏与重复；
   不把模型自称覆盖的 need 当完成证明。记录第一次结果与改进后诊断，冻结新的匹配配置。
4. **再测规模。** 服务稳定性单列、条件顺序平衡，任何披露的重试都计成本并保留原失败。
   200 项正式清单继续未使用。若混合路径没有胜过强摘要，采用更好的摘要路径作为产品
   默认候选，并重新判断原文选择何时值得额外成本，不为坚持现有算法制造弱基线。

新增 adapter、测试数量或文档数量不能代替上述质量改善。当前应把“少而能接着干”作为
优化目标，而不是把“结构化原文复制成功”作为产品胜利。
