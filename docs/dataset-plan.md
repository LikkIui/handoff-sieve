# 公开数据上的接管评测计划

> 日期：2026-10-11
> 状态：已导入固定版本的 500 项公开任务并锁定划分；10 项开发环境已通过原项目正反验收，模型接管正在运行
> 本计划用于验证 v0.4 的核心选择能力，不增加产品框架适配或平台功能。

## 现有数据究竟是什么

- v0.3 的 20 项任务是本项目自编的可执行模拟任务：7 项编码、7 项执行、6 项审查。
  来源是 [`TASK_CATALOG.md`](../evals/takeover/TASK_CATALOG.md) 和
  [`taskpack.py`](../evals/takeover/runnable/taskpack.py)，不是外部项目的数据集。
- 2026-10-10 的 43 次真实 API 任务请求来自同一小型模块的两个接收目标、三个既有
  pilot、SDK 流程及开发复测。43 是请求数，不是 43 个独立任务。
- 真实 API 调用和实际代码验收已经发生，但任务与历史是人为构造的。这些结果用于调试，
  尚不足以证明在公开任务上普遍优于强摘要。旧结果与首次失败继续保留。

## 推荐规模

| 用途 | 不同原始任务数 | 如何使用 |
|---|---:|---|
| 开发集 | 30 | 调整选择提示、检查环境和评分；不计入正式成功率 |
| 正式测试集 | 200 | 按仓库和任务难度分层抽样；运行前固定任务清单与实现版本 |
| 稳定性重复 | 每项 3 次 | 三种条件使用同一接管起点；分别运行接收方 |

主对照为 Full History、按接收需求生成的强模型摘要、HandoffSieve 模型选择原文。
因此正式目标是 **200 × 3 条件 × 3 次 = 1,800 次接管运行**，不是 1,800 个不同任务，
也不是恰好 1,800 次 API 请求。每次接管可能需要多轮模型与工具调用，摘要和选择还有准备调用。

200 是当前产品阶段的工程建议，不是统计上通用的“足够”门槛。一次运行若成功率约 80%，
200 项任务的单组成功率按独立二项近似仍有约 ±5.5 个百分点的 95% 误差范围；方案间
差值应按同任务配对估计，不能把这个范围直接用于差值。重复试验不能替代更多不同任务。
若要声称成功率下降不超过 1–2 个百分点，必须依据实际配对结果另算规模，不能预先保证
200 项足够。同一仓库的任务也可能相关，需公开仓库分布。

可以分批完成固定测试清单，先公开前 100 项的中间结果，再完成 200 项；不能因为中间
结果有利就停止，也不能看完测试失败后改提示再把同一批称作未见测试。需要修产品时，
保留首次结果，修订版复测另行报告；预留未使用任务用于后续确认。

## 数据源选择

### 主数据：SWE-bench Verified

[官方数据集](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)包含 500 个
经过人工质量核验的真实 GitHub Issue–PR 修复任务，可用原项目测试判定修复是否成功。
从中分配互不重叠的 30 项开发任务与 200 项正式任务，剩余任务预留，不参与提示调优。
这是自定义接管实验的划分，不是 SWE-bench 官方发布的新 split。

直接使用官方任务、仓库起始提交和评分器；不把任务重新编写成我们自己的小题。
[评分代码](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py)
检查 FAIL_TO_PASS 和 PASS_TO_PASS，既要修复问题，也要保住原先通过的行为。

任务数据不是现成的 handoff state。优先在这些真实任务上调用模型，保存发送方的实际
调查与工具记录，并在预先固定的工具步骤预算处交接。首次实现可让 researcher 只读仓库，
随后 coder 接管，以便三组确实获得相同的文件起点；不得把手写的“正确研究结论”当作历史。

[SWE-bench experiments](https://github.com/SWE-bench/experiments)也公开执行日志和轨迹
入口。对应任务的轨迹可作为后续补充，但必须检查能否还原中途环境；只截取文字并不能
还原已经修改的文件。使用旧轨迹时另列轨迹来源与发送模型，不与新采集轨迹混称同一种数据。

### 补充来源，不混入首次主结果

| 来源 | 可用于什么 | 边界 |
|---|---|---|
| [SWE-smith trajectories](https://huggingface.co/datasets/SWE-bench/SWE-smith-trajectories) | 大量真实执行的编码 Agent 轨迹，检查长历史、失败尝试和工具消息格式 | 底层修复任务是生成的；不能冒充真实 GitHub Issue，不能与 Verified 任务随意配对 |
| [τ²-bench](https://github.com/sierra-research/tau2-bench) | 后续验证工具任务中途接管，如订票与售后操作 | 单独报告工具任务结果；采用任务声明的最终数据库状态与沟通评分，不能把参考动作序列当唯一答案 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 检查长历史中的事实、知识更新与时序信息保留 | 500 项长期记忆问答，不是代码或工具任务接管；不能拿问答正确率代替 downstream task success |

SWE-smith 的[官方资产说明](https://swesmith.com/getting_started/assets/)提供任务、环境和
轨迹入口。只下载所需样本并固定数据版本；数据页面总行数、轨迹数和不同任务数分别记录，
不能把不同消息格式的重复记录当成新增任务。

## 如何从公开任务做真正的交接实验

1. 固定数据版本、任务 ID 清单和抽样种子。开发集先检查环境与验收；正式抽样不按某种
   方案是否成功筛选。导入失败、环境失败和任务失败分别记录，公布完整分母与排除原因。
2. 在原仓库起始提交上运行发送方，按预定步骤预算停止；冻结当时的消息、工具结果与
   文件状态。同一任务的三种输入均从这一状态开始，所有试验使用相同模型、工具和继续执行预算。
3. 摘要与 HandoffSieve 获得相同的接收目标、需求、原历史与交接预算。强摘要可以判断
   接收任务需要哪些信息，不能只用弱小的通用摘要制造优势；记录实际大小和预算违规。
4. 所有条件都只能看到交接时已经产生的信息。参考修复、隐藏评分信息、最终轨迹结果、
   交接点之后的工具输出不得进入摘要器、选择器或接收方；评分器在完成后独立运行。
5. 按原始任务汇总并计算配对差值。同题多个交接点、多个重复试验不增加不同任务数；
   超时、选择失败、预算失败和接收方失败均保留，不用事后成功复测覆盖首次结果。
6. 同时报告任务成功率、交接 token、选择/摘要准备消耗、后续模型与工具消耗、耗时、
   重试与事件数。共同发送方采集成本单列，明确一次使用与重复接管时的成本，避免只展示 packet 变小。

这组实验是 **基于 SWE-bench Verified 的中途接管评测**，不能把它标成官方 SWE-bench
排行榜成绩，也不能自动推出在所有多智能体任务或其他开源产品上有优势。
